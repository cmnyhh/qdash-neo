写这份表的目的：把「我以为」和「确实如此」分开。旧方案里最贵的错误不是判断错，而是把反推来的假设当成了 API。

## 一、已核实（有源码路径 / 官方文档依据）

### 1. 插件形态与声明

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'qdash-neo'
export const inject = ['agents', 'sessions', 'sessionPersistence', 'tools', 'settings', 'webServer']
export const Config = z.object({ /* @deepseek-ai/schemastery */ })

export function apply(ctx: Context, config: typeof Config.Type) {
  // 一切注册都在这里，卸载时自动清理
}
```

- 三件套 `name` / `inject` / `apply(ctx)`，可选 `Config`。三种写法（函数 / 对象 / 类），需要向其他插件提供能力时用 class 继承 `Service` 并 `super(ctx, 'qdashNeo')`。
- `inject` 声明的服务未就绪时插件停在 `PENDING`，服务消失自动卸载、恢复后重载。可选依赖用 `ctx.get()`。
- 导出的 `Config` **必须是 schemastery schema 对象**，只导出 TS interface 等于没有校验、没有默认值——这是"装了却什么都不发生"的头号原因。
- 依赖包名必须带作用域：`@deepseek-ai/schemastery`、`@deepseek-ai/cordis`。写裸名 `schemastery` 会静默解析失败。

### 2. 入站：把外部消息喂给 agent

```ts
import { createUserMessage } from '@deepseek-ai/dsh-llm'
import { SessionId } from '@deepseek-ai/dsh-session'

const handle = await ctx.agents.create({
  sessionId: SessionId(`qq:g:924183756`),
  agentOptions: { provider, model },
  // setup 回调：可挂 preset、装模型选择
})
handle.agent.followup(createUserMessage({
  content: [{ type: 'text', text }],
  source: { kind: 'user' },
}))
```

三个注入原语的语义差别（`packages/core/agent/src/runtime-types.ts:124`）：

| 方法 | 内部 | 唤醒 | 时机 | 用途 |
|---|---|---|---|---|
| `followup(msg)` | `send(msg,'next-turn',true)` | 是 | 开新一轮 turn | QQ 来消息 |
| `steer(msg)` | `send(msg,'next-step',true)` | 是 | 下一个 step | 打断当前工作 |
| `inject(msg)` | `send(msg,'next-step',false)` | 否 | 等下条消息 | 后台通知、补上下文 |

**关键**：`followup()` 返回的是入队回执，不是结果。不能拿它等答案，答案只能从事件流里取。

`ctx.agents.resume({ resumeSessionId, agentOptions, setup })` 用于跨进程重启续接。同一 session 同时只能有一个 live 持有者，撞车要重试。

### 3. 出站：拿 agent 的回复

```ts
ctx.on('session/event', (session, event) => {
  if (session.header.id !== sessionId) return   // 多会话必须自己过滤
  if (event.type === 'assistant/message') {
    const text = event.data.content.filter(c => c.type === 'text').map(c => c.text).join('')
  }
})
```

事件类型（`docs/subsystems/session.md:27-124`）：

`turn/start` `turn/end` `step/start` `step/end` `user/message` `assistant/chunk` `assistant/message` `tool/call` `tool/result` `todo/write` `request/header`

- `assistant/chunk.data.chunk.type` ∈ `reasoning-delta` / `text-delta` / `usage`
- `assistant/message` 是**已提交**的整条消息，QQ 侧只取这个，不接 delta
- `tool/call` 形状 `{ turn, step, callId, name, arguments }`，`tool/result` 靠 `callId` 配对
- 事件是 **post-commit fire-and-forget**，观察者异常被隔离；**不保证处理时序**，要自己串行化
- 另有 `agent/assistant-stream`（瞬态、不写日志），只为打字机效果，不用于业务

**运行时不变量：模型可见 = 已记录。** 任何要送进模型请求的内容，必须能从会话日志重建，否则直接报错。这条决定了「补投漏掉的消息」不能只塞内存——必须走 `followup` 形成日志事件。

### 4. 审批拦截（旧方案的"唯一未验证项"，已确认存在）

```ts
ctx.on('approval/request', (req, next) => {
  const sid = req.agent.session.header.id
  if (!sid.startsWith('qq:')) return next()        // 非本通道，交给别的 answerer
  return askOnQQ(req.toolName, req.reason, req.signal)
}, { prepend: true })                              // 插到 web answerer 之前
```

- 签名（`packages/interaction/user-approval/src/index.ts:30`）：
  `'approval/request'(req: ApprovalRequest, next: () => Promise<ApprovalOutcome>): Promise<ApprovalOutcome>`
- `ApprovalRequest = { agent, toolName, callId?, reason?, signal? }`
- 应答四态：**`allowed-once` | `rejected` | `cancelled` | `unavailable`**
- 只有 `allowed-once` 是放行，其余全部 fail-closed
- answerer 是**决定者**不是发起者；`ctx.approval.request()` 才是发起方（我们不用）
- 超时参考实现：10 分钟自动 `rejected`；`req.signal` abort → `cancelled`

→ 结论：**审批转发可以做，`{prepend:true}` 保证抢在 Web UI 前面应答**。旧方案 §9 的这一条可以划掉。

### 5. 配置有两层，必须分开用

| | 静态 Config（base 层） | 用户层（user） |
|---|---|---|
| 谁改 | 部署方 | 终端用户 |
| 在哪改 | patch 层 YAML | 界面表单 |
| 声明 | `export const Config`（schemastery） | 无独立声明，挂在同一个 ns 下 |
| 生效 | 重启 | `applies: 'live'`，保存即生效 |
| 放什么 | 端口、路径、端点、密钥 | 开关、阈值、偏好 |

**关键修正（源码级）**：`ctx.settings` 上**没有 `register()`**，也**没有 `settingsNamespace()` 这个导出**。`ctx.settings` 是 `SettingsForms` 服务，API 只有五个：

```ts
ctx.settings.configure({ auto?: boolean }, owner?: Fiber): () => void
ctx.settings.prepareDocument(): Promise<string>
ctx.settings.describe(opts?: { redactSecrets?: boolean }): SettingsDescriptor[]
ctx.settings.update(ns: string, patch: object, expectedRevision?: number): Promise<void>
ctx.settings.replace(ns: string, section: object, expectedRevision?: number): Promise<void>
ctx.settings.mutate(ns: string, ops: readonly SettingsPathOp[], expectedRevision?: number): Promise<void>
```

`SettingsDescriptor`（`dsh-settings/lib/types/index.d.ts:8`）：

```ts
{ ns, autoGenerate, schema, value, revision, base?, user?, applies: 'live', secrets? }
```

语义：
- **`ns` 是「一个 profile plugin entry 的 nominal id」**（`SettingsNamespace = Branded<'SettingsNamespace'>`），由 patch 里该插件的 `id` 决定，不是自由命名的字符串 → 我们的 ns 就是插件在 patch 里的 id
- 表单**从 `Config`（schemastery）自动派生**，`autoGenerate` 决定没有自定义页面时 UI 是否自动生成
- `value` = schema 默认值 → `base`（composition 层）→ `user`，逐层覆盖后的结果
- `user` 里出现的字段 = 用户覆盖过的字段
- `revision` 单调递增，写回时作为 `expectedRevision`，stale 写入抛 `SettingsConflictError`（带 `expected` / `actual`）
- `applies` 目前只有 `'live'` 一种取值

**推论**：想给用户可改的运行时配置，唯一正统做法是**把这些字段也放进 `Config`**（schemastery 声明 + `.default()`），然后靠 `describe()` / `update()` 读写。不存在"另一套用户配置 schema"这回事。

**patch 层的两个坑**：
1. patch 按 entry 的 `id` 定位，`id` 定了不能改，改了所有覆盖层静默失效（只有 warn）
2. `config` 是**整块替换不是深合并**：想改一个键，也得把整块重述 → 所以每个字段的 `.default()` 是必需品

覆盖顺序（后者压前者）：`profile.bundles` → profile 的 `cordis.patch.yml` → `$DSH_HOME/cordis.patch.yml` → `--patch` 覆盖层。

### 6. 生命周期与清理

- Fiber 状态机：`PENDING → LOADING → ACTIVE / FAILED`，`ACTIVE → UNLOADING → DISPOSED`
- 通过 `ctx` 注册的一切（工具、事件、路由、服务）**卸载时自动回收**，不用手写 removeListener
- 需要显式释放的资源（socket、sqlite、http server）走 `ctx.effect(() => disposer)`
- ⚠️ 多个 disposer **逆序开始但并发执行**，有顺序依赖的清理必须合进同一个 `ctx.effect`

### 7. 发布与安装

- `package.json` 声明 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" } }`
- peer 依赖：`@deepseek-ai/cordis@^4.0.1` + `dsh-agent` / `dsh-session` / `dsh-llm` / `dsh-tools` / `dsh-scope` / `dsh-system-prompt`
- 安装：`dsh plugin --profile web add github:owner/repo` 或 npm 包名；本地开发用 `file:` 或 `--patch`
- 装完**必须重启 DSH**（Host 半在启动时注册路由，浏览器半在页面加载时注册槽位）
- 临时停用：在 profile patch 里对该 `id` 设 `disabled: true`

## 二、源码验证结果（对照 dsh `0.2.1-rc.2` 的 `.d.ts`）

以下全部取自 `node_modules/@deepseek-ai/*/lib/types/*.d.ts`，不是社区文档转述。验证方式见文末「验证方法」。

### 2.1 路由注册（原「未验证项 #1」，已定）

`dsh-host-webserver/lib/types/index.d.ts`：

```ts
export type WebRouteKind = 'exact' | 'prefix'
export interface WebRoute {
  kind: WebRouteKind
  path: string      // 绝对路径，不允许尾斜杠
  handler: (req: IncomingMessage, res: ServerResponse) => void | Promise<void>
}
register(route: WebRoute): () => void
registerUpgrade(route: { path: string; handler: (req, socket: Duplex, head: Buffer) => ... }): () => void
registerFallback(handler: WebRoute['handler']): () => void   // 单 owner
tapIndex(transform: (html: string) => string): () => void
getOrigin(): string
get port(): number | undefined
get protocol(): 'http:' | 'https:'
```

要点：
- **`kind` 只有 `'exact'` / `'prefix'` 两个取值**，`'prefix'` 匹配 `p` 和 `p/<anything>`
- handler 是**原生 node handler**，自己完全拥有响应生命周期（SSE 可长挂）
- 重复的 `(kind, path)` **直接抛错** —— 路由模式是组合级契约
- **`registerFallback` 只能有一个 owner**，宿主 Web 组合已经占了（SPA dist server）。我们的控制台**必须用 `prefix`，绝不能抢 fallback**
- 有 `registerUpgrade`，可以做 WebSocket → 控制台实时推送不用轮询
- `Config.host` 是必填的具体地址字面量，**wildcard 地址在加载期就被拒**；`port: 0` 由 OS 分配，之后读 `port` getter

### 2.2 提问转发：`ask_user_question` 是工具（原「未验证项 #2」，已定）

`dsh-tool-ask-user` / `dsh-user-questions` / `dsh-client-ui-tool` 里都是**工具**语义：
- `dsh-tool-ask-user/lib/types/timed.d.ts`：`timed ask_user_question` 工具定义
- `dsh-user-questions/lib/types/projection.d.ts`：把 `ask_user_question` 的**工具事件**折叠成"可回答问题集"

→ 提问转发**不做事件订阅，做工具层拦截**（`tools` 的 pre/post 管道，或 `session/event` 里的 `tool/call` 判 `name === 'ask_user_question'`）。

### 2.3 preset 挂载：`meta.agentPreset`（原「未验证项 #3」，已定）

`dsh-agent/lib/types/index.d.ts` 的 `CreateAgentOptions`：

```ts
readonly meta?: {
  cwd?: string
  parentSession?: SessionId
  isSeeded?: boolean
  origin?: 'subagent'
  delegationDepth?: number
  agentPreset?: string    // ← preset 在这里，不需要 setup 回调
}
readonly agentOptions?: AgentOptions
readonly signal?: AbortSignal
readonly setup?: AgentSetup
```

`setup` 的定位是 **"composes, it never drives"**：建会话时用它挂 scoped 工具、prompt 段、监听器，**不能用它驱动 agent**。驱动只能等 `create()` 返回之后。

### 2.4 取消接口（原「未验证项 #6」，已定）

`Agent.cancel(options?: CancelOptions)`，`CancelOptions = { keepInbox?: boolean }`。
`keepInbox: true` 保留待处理/转向的 inbox 项，只中止当前 turn —— 这正是「暂停会话」要的语义。

另有 `Agent.status: 'idle' | 'running'`、`whenIdle(): Promise<void>`、`runMaintenance(task)`。

### 2.5 注入三原语（修正措辞）

`dsh-agent/lib/types/runtime-types.d.ts`，三者都**返回 `void`**（入队即返回，不返回结果）：

```ts
send(message: UserMessage, target: InboxTarget, wakeup: boolean): void
followup(message: UserMessage): void   // 独立成一轮并唤醒
steer(message: UserMessage): void      // 最近一个 step 边界消费
inject(message: UserMessage): void     // 不唤醒，等下个 pre-step
```

`followup` 的注释明确写：**"becomes the sole ordinary message of its own turn"** —— 一条消息一轮。批量补投要自己合并成一条，否则一次断线重连会拉出 N 个 turn。

### 2.6 事件表（14 类，修正两处）

`dsh-session/lib/types/types.d.ts:256` `SessionEventMap` 实际成员：

`turn/start` `turn/end` `step/start` `step/end` `user/message` `developer/message` `system/message` `assistant/message` `assistant/attempt` `tool/call` `tool/result` `request/header` `request/context` `session/end-seed`

修正：
- **没有 `assistant/chunk`** —— delta 走 `agent/assistant-stream`（瞬态、不写日志）
- **没有 `todo/write`** —— 那是插件（`dsh-tool-todo`）扩展进 `SessionEventMap` 的，不是核心事件

`assistant/message` 的形状（这条最有价值）：

```ts
'assistant/message': {
  turn: number; step: number;
  message: AssistantMessage;
  stream: AssistantStreamRecord[];
  usage?: TokenUsage;        // ← 真实 token 用量，跟着消息一起走
  interrupted?: true;        // ← turn 中途被取消时的前缀标记
}
```

→ **记账不需要估算 token，`usage` 直接给**。而且没有独立的 usage 记录，必须在这里收。
→ `interrupted: true` 是「暂停/取消」在出站侧的判定依据。

### 2.7 `session/event` 是 scope 派发

`'session/event'(this: Scoped<Session>, session: Session, event: SessionEvent): void`

`@deepseek-ai/dsh-scope` 提供 scope-filtered dispatch。用 scoped ctx 注册监听，**天然只收该 agent 的事件**，比手动比 `session.header.id` 更不容易错。多会话场景优先用 scope，兜底才用 id 比较。

### 2.8 模型绑定映射（对应旧方案 §5.7）

`AgentOptions = { provider?: string; model?: string; reasoningEffort?: ReasoningEffortId; maxTokens?: number }`

→ 三层绑定直接落在这个结构上，不需要另造一层抽象。

### 2.9 工具定义（对应旧方案 §5.6）

`ToolDefinition extends ToolSchema`，`output: ToolOutputDefinition` **是必填**（mandatory canonical output declaration），`execute(args, exec): Promise<unknown>`。

→ 工具 id 想稳定，靠 `name` 字段；宿主改名对我们是**不可能事件**（我们自己注册的工具名自己定），所以旧方案里"用稳定 id 防宿主改名"的焦虑只适用于**外部 MCP 工具**，不适用于自己注册的。

## 三、运行时验证（2026-10-26 全部跑完，**无剩余待验项**）

### 3.1 审批与 `tool/call` 的时序 —— 审批在 `tool/call` **之后**

做法：给现有工具 `working_directory` 在 `tools/pre-execute` 里返回 `{kind:'ask'}`，
`approval/request` 应答前故意延迟 1200ms，然后按会话日志的 seq 定序
（`approval/asked` / `approval/decided` 本身就是会话事件，`dsh-user-approval/lib/index.js:132,139`）。

| seq | 事件 | 相对时间 |
|---|---|---|
| 14 | `assistant/message`（含 tool-call 块） | +3649ms |
| 15 | `tool/call` | +3650ms |
| 16 | `approval/asked` | +3652ms |
| 18 | `approval/decided` = `allowed-once` | +4869ms |
| 19 | `tool/result` | +4874ms |

**结论 1：`tool/call` 先落盘，审批在它之后、工具执行之前。**

**结论 2：拒绝也是完整的一轮。** outcome=`rejected` 时 `tool/result` 照样产生，内容是
`Error: the user rejected tool "working_directory"`、`isError: true`，`turn/end` 仍是
`{kind:'completed'}`。

→ **超时拒绝对模型天然可见**，不需要我们再补一条"被拒了"的消息；
→ QQ 侧转发审批时，"已拒"由模型自己说出来，内核不用另写文案（只要保证它的输入里有这个结果）。

### 3.2 同 session 双持有者的报错形态 —— **不可靠，必须自建互斥**

| 场景 | 抛出的东西 |
|---|---|
| 内存里有 live 持有者时再 `create` 同 id | 普通 `Error`：`session "<id>" already exists`，`code` 与自定义字段**全无** |
| `dispose()` 之后（内存已无持有者）再 `create` 同 id | `SessionAlreadyExistsError`（`ownProps: sessionId, name`）—— 磁盘记录还在 |
| `dispose()` 之后 `resume()` 同 id | **成功** |
| 对照：换新 id 立刻 `create` | 成功（所以失败只与"该 id 已被占用"有关，不是 store 坏了） |

源码位置：`dsh-session/lib/index.js:1805` 是 `if (this.store.has(sessionId)) throw new Error(...)`；
`SessionAlreadyExistsError` 定义在 `dsh-session-persistence/lib/index.js:34`。

**结论 1**：认错只能靠 `err.name`（没有 `code`）。而 live 冲突连 `name` 都是 `Error`，
**与"真失败"不可区分** → `ensure()` 必须自建互斥（内存单飞表），把"已有持有者"当正常分支，不当异常。

**结论 2**：`dispose()` 不是"删除会话"——内存里没了、磁盘上还在。**重启后恢复必须 `resume()`**，
`create()` 会稳定失败。这条直接改写了 `ensure()` 的实现（见 03）。

### 3.3 profile 级插件的 Client 半能否上屏（技术备选，最终未采用）—— ✅ 已验通

**实测记录**（探针包 `qdn-probe`，加 `dsh.client` + `exports["./client"]` + `lib/client.js`，重启 `dsh web`）：

## 五、对原项目（Derpyu520/qq-bridge）的核实结论

它确实是「独立进程 + DSH Web API」：Cookie 离线铸造（用 `~/.dsh` 里持久化的签名密钥）、`/api/<ns>/<method>` 斜杠 RPC、`/api/remote.mux` 事件流、`session/control` 读队列。0.1.7 起进程启动 token 只在内存不落盘，所以它必须去铸造 Cookie——这正是重构的起点。

它的坑清单直接可继承（见 02），其中三条最值钱：
1. **SnowLuma 的 HTTP token 与 WS token 不是同一个值**，所以首次 WS 连接几乎必然失败一次，自愈后正常
2. **`get_login_info` 不返回 `good` 字段**，用它做健康判断会变成永不触发的死代码
3. **`followDiscoveredEndpoint` 会覆盖人工配置的 wsUrl**，多实例场景必须关掉

它的 `reserved2` 已经是「文本不自动转发，AI 自己用 MCP 工具看消息/发言/潜水」——与本方案的 `assertive` 一致；我们新增的 `judge` 档是在它前面加一道便宜判定，不改变这套自主权模型。

## 六、几个必须记住的细节（源码里读出来的，容易踩）

**1. `AgentHandle = { agent: Agent; dispose(): Promise<void> }` —— 只有两个成员。**

`dispose()` 的语义（`dsh-agent/lib/types/index.d.ts:7206` 附近注释）：停循环 → 等退出 → 反注册 → **把 session 从 store 里移除** → 收尾 scope。

→ **绝不能拿 `dispose()` 当"暂停"用**。暂停要用 `agent.cancel({ keepInbox: true })`；`dispose()` 会把会话记录一起删掉，`resume()` 也无从续接。
→ 会话映射要活过进程重启，靠的是 `ctx.agents.resume({ resumeSessionId, ... })` + `inject: ['sessionPersistence']`，不是靠持有 handle。

**2. `resume()` 必须 `inject: ['sessionPersistence']`**，它的注释写明「must be called after `ctx.sessionPersistence` exists」。

**3. 同一 session 同时只能有一个 live 持有者**（见待验项 2）。我们的 `ensure(chatKey)` 必须做成幂等：先查自己的映射表 → 有 live handle 直接复用 → 没有才 `create`/`resume`。

**4. `followup` 一条消息一轮**（见 2.5）。补投多条要合并成一条 `UserMessage`，否则连发 10 条历史消息 = 10 个 turn = 10 次模型调用。

**5. `usage` 只在 `assistant/message` 上**，且注释说"没有独立的 usage 记录"。预算刹车的数据源就在这里，别去别处找。

**6. 控制台 UI 只有一条合法通道：`ctx.slots`。**

- `ctx.slots.register({ name, id|key, order, label, locale, inject }, Component)` / `ctx.slots.inject(key, cb)`，返回 disposer，随 fiber 回收（`dsh-client-ui-renderer/lib/types/client/registry.d.ts`）
- 「加一个选项卡」= `sidebar.panellist`（list，`id`）+ `main`（keyed，`key` 同名）。官方 `ui-schedule`、`ui-plugin-manager` 都是这两句（`dsh-client-ui-schedule/lib/client.js`）
- 「加一页配置」= `settings.section`（整页）或 `plugins.row.config` / `plugins.bundle.config`（插件页内，keyed by 包名）
- `root` 已被 `ui-layout` 的 AppFrame 占着，**注册上去会顶掉整个框架**；`sidebar` / `rightbar` / `main` 里 `conversation` key 同理，都是"替换"不是"添加"
- `registerFallback` 只有一个 owner，宿主 SPA 占着 → 我们不可能接管控制台页面的入口
- 浏览器半的装载：`@deepseek-ai/dsh-client-modules` 增量扫描 Host Loader 里声明 `dsh.client` 的包，编进启动图，产物形态是 `window.__ModuleLoader__.load({ id, factory: (require) => {...} })`，手写即可、不需要打包器
- **实测错误形态（2026-10-26，见 §三 第 3 项）**：Client 半写坏**不会白屏**，而是**静默从启动图里消失**。
- **本方案不采用这条路**（理由 04 §10.1）：控制台是自己的端口、自己的页面，宿主只借 HTTP 入口。这一节留档，是为了"以后想改主意时，不必再验一遍"。
- 产物形态是 `window.__ModuleLoader__.load({ id, factory: (require) => {...} })`，手写即可，不需要打包器
